# 11 架构课：BFF + Worker 分层

> 对应网站页签：🧪 动手实验室 → 案例课。数据源 `src/data/g4-labs.ts` 的 `labArchitecture`（案例源自一个真实的 AI 音频编辑项目）。

## 先说结论

这是系列的收官篇。前面十篇都在讲「一个服务怎么写」，这一篇讲「服务怎么拆」。核心只有一个判断：**当请求链路里出现耗时重活，就把重活拆到独立的 Worker 层，请求链路只负责接活、记账、派活**。这个模式是后端架构的第一原则，名字可以叫异步任务、生产者-消费者、BFF + Worker，本质都是它。

## 案例：AI 音频项目的分层

原项目结构：小程序 → 8087 BFF（鉴权/MySQL/Redis）→ 8088 Worker（ffmpeg/COS 对象存储）。用户上传音频裁剪一段，为什么拆两层？

- ffmpeg 转码一跑几秒到几分钟，HTTP 请求等不了这么久（超时、重试、连接占用全是灾难）。
- 转码吃 CPU，和「响应登录、查询」这类轻请求混在一个进程里，互相拖累。
- 转码任务需要排队削峰：十个人同时上传， Worker 按能力消费队列。

于是分层（网站案例课的五语言对照核心段，Go 版）：

```go
// 8087 BFF：只编排，不跑 ffmpeg
r.POST("/jobs", auth(), func(c *gin.Context) {
    job, _ := store.Insert(userID(c), bindJob(c))   // 1. MySQL 记账
    rdb.LPush(ctx, "audio:jobs", job.ID)            // 2. Redis 排队
    worker.Dispatch(job.ID)                          // 3. 通知 Worker
    c.JSON(200, gin.H{"id": job.ID, "status": "queued"})
})

// 8088 Worker：只处理，不面对前端
r.POST("/internal/jobs", func(c *gin.Context) {
    wav := cos.Download(job.Src)
    out := ffmpeg.Trim(wav, job.Start, job.End)
    url := cos.Upload(out)
    callback.Notify(job.ID, url)                     // 4. 回调通知完成
})
```

逐行读这段，BFF 的三次动作各是一个必修概念：

1. **先落库**：任务先持久化到 MySQL，服务重启任务不丢。这是「可靠」的底线——只排进内存队列，进程一崩任务蒸发。
2. **再排队**：Redis 的 List 当队列（`LPUSH` 进，`BRPOP` 出）。第 08 篇说「Redis 不只是缓存」，就是指这种用法。
3. **最后派活**：HTTP 通知 Worker，或 Worker 自己轮询队列。生产级会用专门的消息队列（RabbitMQ/Kafka），但原理相同。

`status: "queued"` 这个响应是整个模式的脸：**请求立即返回「已受理」，而不是「已完成」**。前端拿着 job id 轮询或等推送——这就接上了第 09 篇的 SSE，以及你前端写过的「任务进行中」进度条。

## 边界纪律：为什么 `internal` 这个词很重要

Worker 的路由挂在 `/internal/jobs`——「内部接口，不对外」。这条纪律是分层的全部意义：

- BFF 面对外：鉴权、限流、参数校验、登录态，全在这一层做。
- Worker 面对内：只接受 BFF（或其他可信服务）的调用，**不重复做鉴权**，网络层面用内网隔离/防火墙保证外部摸不到。
- 各层只依赖契约（`{ id, status }`），不依赖对方实现。任何一层可以用任意语言重写——事实上原项目就是四语言等价实现过，网站案例课的 Rust 版是补写的同构草稿，五语言对照在这里的意义是：**架构与语言无关**。

初学者最常见的翻车是把重活塞进 BFF 的请求处理里「先跑完再返回」。判断要不要拆 Worker 的唯一标准回到第 08 篇那句话：**这个操作让用户等几秒以上算不算正常？** 算——拆；不算——别拆，多一层就多一份运维成本（YAGNI 同样适用于架构）。

## 毕业标准与下一步

能独立做到以下三件事，本系列就算毕业：

1. 从零设计并跑通一个带 JWT 鉴权、MySQL 持久化、有日志和错误处理的小 API（ laboratories 三个实验室是你的参照物和校准器）。
2. 拿到一个新需求，能判断它该同步返回还是拆异步任务。
3. 读任何一门你「不会」的语言写的后端代码，能靠网站字典页 + 本系列建立的心智模型猜出个八九不离十。

之后的方向按兴趣选：深入某一门语言（网站 frameworks.ts 给每门语言列了 3–5 个主流框架的定位对比）、深入数据库（索引原理、主从复制）、或深入架构（消息队列、微服务、可观测性）。网站和 `src/data/` 还会继续扩充，这个系列也可以跟着长——所有内容的事实源都在这个仓库里，欢迎对照核验。
